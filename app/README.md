# מתכנן הארוחות

אפליקציית ווב פרטית לתכנון ארוחות במשק בית. מובייל-תחילה, עברית RTL,
בלי שרת ובלי חשבון — כל המצב יושב ב-`localStorage` של המכשיר.

בלי build, בלי תלויות, בלי בקשות רשת חיצוניות. ES modules טהורים.

---

## המסכים

| טאב | מה הוא עונה עליו |
|---|---|
| **היום** | "מה אוכלים עכשיו" + סימון שזה קרה. טאב ברירת המחדל. |
| **השבוע** | תכנון: איזו מנה בכל אחת מ-21 המשבצות (7 ימים × 3 ארוחות). |
| **קניות** | מה לקנות, מקובץ למדפי סופר, עם סימון בעגלה. עובד אופליין. |
| **מזווה** | מה כבר בבית. מקוזז אוטומטית מרשימת הקניות. |
| **מאקרו** | מה נאכל בפועל מול היעדים, לכל פרופיל. מתאר, לא שופט. |

## מפת המודולים

**לוגיקה טהורה** — בלי DOM, בלי גישה ל-store, נבדקת ישירות:

| קובץ | אחריות |
|---|---|
| `normalize.js` | המרות יחידות, סכימת רשימת קניות, חישוב מאקרו |
| `plan.js` | ארוחות, מצב יום, רצף בישול, מפתחות שורות קנייה |
| `pantry.js` | קיזוז המזווה מול דרישות השבוע |
| `catalog.js` | מיזוג מנות/מצרכי זרע עם עריכות המשתמש |
| `profiles.js` | מי במשק הבית, יעדים, וניקוי משבצות בהוצאת אדם |
| `history.js` | מתי בישלנו מה, והעתקת שבוע קודם |
| `suggest.js` | דירוג מנות למשבצת ריקה, והנימוק לכל הצעה |
| `extras.js` | נשנושים ומשקאות — מאקרו, קנייה, והוספה מהירה |

**מצב ונתונים:**

| קובץ | אחריות |
|---|---|
| `store.js` | התמדה, נרמול קלט פגום, גלגול שבוע, סנכרון בין טאבים |
| `data.js` | נתוני זרע — מנות, מצרכים, מדפים. **בקוד, לא באחסון.** |

**ממשק** — `app.js` (רישום מסכים), `ui-today/week/list/pantry/score.js`
(מסכים), `ui-overlay.js` (מחסנית שכבות ולבני טופס), `ui-sheet.js` (בורר
מנה), `ui-dish-editor.js` / `ui-ingredient-editor.js` / `ui-profiles.js`
(טפסים), `ui-strip.js` (פס השבוע), `ui-suggest.js` (שכבת אישור ההצעות),
`ui-extras.js` (נשנושים במסך היום).

**זרימה חד-כיוונית:** המסכים קוראים מה-store וכותבים דרך `store.update`
בלבד. `app.js` מחזיק את המנוי היחיד שמרנדר מחדש. אף מסך לא מייבא בחזרה
מ-`app.js` — אין מעגל תלויות.

## מודל הנתונים

```js
{
  schema_version: 1,
  plan: {
    week_start: "2026-07-26",          // תמיד יום ראשון
    slots: {
      "2026-07-28.dinner": {            // מפתח: תאריך.ארוחה
        dish_id: "dish.schnitzel_chips",
        servings: 2,
        eaters: ["p1", "p2"],
        status: "planned"               // planned | cooked | ate_out | skipped
      }
    },
    extras: {                           // נשנושים ומשקאות, רשימה ליום
      "2026-07-28": [{
        id: "x1",
        ingredient_id: "ing.coffee_black",
        qty: 1, unit: "unit",
        kind: "snack",                  // snack | drink
        eaters: ["p1"],
        planned: false, eaten: true     // שתי עובדות, לא ציר אחד
      }]
    },
    checked: { "ing.onion": true }      // סימוני קנייה, מתאפסים בגלגול שבוע
  },
  profiles: [{ id, name_he, targets: { kcal, protein_g, fat_g, carbs_g }, dislikes: [], archived }],
  pantry:      { "ing.onion": { qty: 300, unit: "g" } },
  dishes:      { "dish.u1": { ... } },  // מנות משתמש + עריכות של מנות זרע
  ingredients: { "ing.u1": { ... } }    // מצרכי משתמש
}
```

### מדיניות סכמה

`SCHEMA_VERSION` הוא **1** ולא עלה מאז. כל התוספות עד היום היו נקיות —
שדות חדשים בלבד. `coerceState` פורס את ה-raw ושומר שדות שהגרסה הזו לא
מכירה, כך שגרסה ישנה במטמון לא מוחקת נתונים של גרסה חדשה.

להעלות את הגרסה **רק** כששינוי אינו תואם אחורה. הערך מנעילת כתיבה
(`schema_version` עתידי → האפליקציה לא כותבת בכלל) גדול מהערך של מספור
מסודר.

## החלטות שקל להפוך בטעות

הרשימה הזו קיימת כדי שהחלטה נכונה לא תתהפך בסיבוב הבא. כל אחת מהן
מתועדת גם בראש הקובץ הרלוונטי.

### אין המרה מנוחשת — בשום מקום

`toBase` מחזיר כמות **מסומנת** כשאי אפשר להמיר, לא שגיאה ולא אפס שקט.
"גביע יוגורט אחד" בלי `unit_weight_g` מגיע לרשימת הקניות כפריט "לבדוק
ידנית" עם הכמות המקורית. אותו כלל בדיוק חל על קיזוז המזווה.

מספר מומצא ברשימת קניות גרוע ממספר חסר — הראשון נראה כמו ידיעה.

### מנות זרע נשארות בקוד; עריכה כותבת העתק

הפיתוי: להעתיק את כל הזרע ל-`localStorage` בטעינה הראשונה ומשם לערוך.
המחיר: תיקון בנתוני זרע (ערך תזונתי שגוי, שם, זמן הכנה) לעולם לא מגיע
למי שכבר פתח את האפליקציה פעם אחת.

לכן `catalog.js` ממזג: הזרע בקוד, עריכה שומרת העתק תחת אותו מזהה,
ההעתק גובר. מחיקת ההעתק היא "שחזור לגרסה המקורית" וקיימת בממשק.

### ארכיון, לא מחיקה — למנות ולאנשים כאחד

משבצות מצביעות על מנה לפי מזהה ושורדות שבועות אחורה. מחיקה הייתה הופכת
כל היסטוריה שמצביעה עליה ל"מנה לא מוכרת" — כולל מסך המאקרו של שבועות
שכבר נאכלו. מנה בארכיון יורדת מהבורר וממשיכה להיפתר בכל מקום אחר.

**אותו נימוק לפרופילים, ובחדות אף גדולה יותר:** `slot.eaters` מחזיק
מזהי אנשים, וחישוב המאקרו מחלק את המנות במספרם. מחיקת פרופיל הייתה
משאירה מזהה יתום בתוך `eaters`, והמחלק היה ממשיך לספור אדם שכבר לא
קיים — כלומר להציג לכל השאר **פחות ממה שהם באמת אכלו**.

הוצאת אדם ממשק הבית מנקה את `eaters` **מהשבוע הנוכחי והלאה בלבד**.
שבועות שעברו נשארים כמו שהם, כי המאקרו שלהם היה נכון כשהוא נאכל.
משבצת שהוא היה האוכל היחיד בה נמחקת — להשאיר אותה עם `eaters` ריק היה
גרוע יותר, כי `coerceSlots` ממלא רשימה ריקה במשק הבית הנוכחי והמנה
הייתה מוקצית בשקט למישהו אחר.

### המזווה לא מתעדכן לבד אחרי "בישלתי"

הפיתוי מובן — סימון הבישול כבר קיים. אבל האפליקציה יודעת כמה המתכון
*נוקב*, לא כמה נכנס לסיר ולא אם נשאר חצי בצל. מלאי שמחסיר מספרים שלא
קרו מצטבר לשקר, והשקר מתבטא במקום הגרוע ביותר: רשימת קניות שמחסירה
פריט שאין בבית.

מזווה ידני שגוי הוא באחריות מי שהקליד. מזווה שמחסיר לבד שגוי בשקט.

### מצרך בלי ערכי תזונה הוא מצב תקין

הדרישה היחידה ליצירת מצרך היא שם. בלי `nutrition_per_100` המנה מסומנת
"חלקי", ובלי `unit_weight_g` היא נופלת למסלול הידני — שני מסלולים
שנבדקים. לחייב ארבעה ערכים כדי להוסיף "פטרוזיליה" היה גורם לאנשים
להמציא מספרים, וזה בדיוק מה שהמנוע נועד למנוע.

ערכים חלקיים (קלוריות וחלבון בלבד) נשמרים חלקיים ומסמנים את המנה
כחלקית — לא מושלמים באפס.

### הריבוע בפס השבוע מתמלא רק כשהיום סגור

כל עוד יש ארוחה מתוכננת שלא הוכרעה, היום "מתוכנן" — גם אם כבר בישלת
בבוקר. אחרת גובר מה שקרה בפועל: בישלנו ← בחוץ ← דילגנו.

**הרצף שואל שאלה אחרת** — "בישלת בבית לפחות ארוחה אחת?" ולא "סגרת את
היום?". ארוחת בוקר מבושלת בזמן שהערב פתוח לא שוברת רצף באמצע היום.
ולהיום יש ארכה: בשש בערב עוד לא בישלת, וזה לא מאפס רצף של שבועיים.

### הצעה נושאת נימוק, ולעולם לא נכתבת לבד

ציון התאמה ("87%") היה בדיוק המספר המומצא שכל המנוע נועד לא לייצר: הוא
נראה כמו ידיעה ואי אפשר לחלוק עליו. לכן כל הצעה מחזירה `reasons`
בעברית, וכל אות דירוג שמזיזה את הסדר גם אומרת את עצמה במילים. אות
שאין לה מה לומר לא משפיעה על הדירוג.

**וכלום לא נכתב בלי אישור.** הכפתור יכול היה למלא את כל המשבצות
הריקות בלחיצה, כמו "העתקה משבוע שעבר" — אבל ההעתקה מחזירה החלטות
שהמשתמש כבר קיבל, וההצעה מייצרת החלטות שלא קיבל מעולם. מילוי שקט של
21 משבצות מצטבר לתפריט שאיש לא בחר, והוא מתגלה בסופר. אותו נימוק
בדיוק כמו המזווה שלא מתעדכן לבד אחרי "בישלתי".

שלוש עדינויות שהתגלו רק בבנייה, וכל אחת נעולה בבדיקה:

- **קנס החזרה מוכפל ולא רווי.** גרסה שנתנה −8 לשתי הופעות ועצרה שם
  הנחיתה את כל המנות על אותה רצפה ברגע שכולן הגיעו לשתיים; שובר
  השוויון לפי שם הכריע תמיד לאותו צד, ואותה מנה הוצעה 16 פעם ברצף.
- **ההיסטוריה והחזרה חולקות את ציר הזמן ולא חופפות.** משבצת שכבר
  בושלה אינה נספרת כ"חזרה", אחרת מנה שבושלה אתמול קיבלה עונש כפול
  והציגה שני נימוקים לעובדה אחת — "בישלתם אתמול · כבר בתפריט השבוע".
- **אותה מנה לא מוצעת פעמיים באותו יום.** זו הפסילה היחידה במנוע ולא
  שקלול, כי קנס לבדו לא מנע אותה: כיסוי מזווה מלא גבר עליו. היא נסוגה
  כשאין ממה לבחור — ספרייה קטנה משלוש ארוחות תקבל חזרה ביום, וזו עדיין
  תשובה טובה יותר ממשבצת ריקה בלי הצעה.

**הכיסוי נמדד מול המזווה כפי שהוא רשום**, בלי לנכות את מה שכבר תפוס
בשביל שאר השבוע. לכן הנוסח הוא "כל המצרכים במזווה" — אמירה על המלאי,
שהיא נכונה — ולא "אין מה לקנות", שהיא הבטחה. רשימת הקניות נשארת
הסמכות היחידה על מה חסר.

### נשנוש הוא שתי עובדות, לא סטטוס אחד

`planned` ו-`eaten` נראים כמו שני מצבים על ציר אחד, אבל הם בלתי תלויים
וכל אחד מזין מסך אחר:

| planned | eaten | מה זה | לאן זה נכנס |
|---|---|---|---|
| ✓ | | בתוכנית, טרם נאכל | רשימת הקניות |
| ✓ | ✓ | תוכנן ונאכל | קניות **וגם** מאקרו |
| | ✓ | נשנוש שקרה | מאקרו בלבד |

סטטוס יחיד היה מאבד את ההבחנה בין "אכלתי תפוח שתכננתי" לבין "אכלתי
עוגייה אצל חברים" — והראשון צריך להופיע ברשימת הקניות בעוד השני לא
אמור להופיע בה לעולם. מתוכנן שכבר נאכל **נשאר** ברשימה, מאותו היגיון
שמשבצת מסומנת "בישלנו" נשארת בה: קונים לפני, לא אחרי.

**המקטע הזה נמדד בחיכוך של שנייה אחת.** נשנוש מוזן עשרות פעמים בשבוע,
וכל הזנה מתחרה מול "לא בא לי עכשיו". לכן המסלול הראשי הוא צ'יפ בהקשה
אחת, מדורג לפי מה שבאמת חוזר, והשכבה קיימת למה שהצ'יפים לא מכסים —
לא להפך. בורר שדורש חיפוש, כמות ובחירת אדם יינטש אחרי יומיים.

**התוספות מצביעות על מצרך ולא על מנה.** נשנוש הוא כמעט תמיד פריט אחד,
ותמיכה במנות הייתה מכפילה כל מסלול (מאקרו, קנייה, בורר) בשביל מקרה
שכבר יש לו בית: מי שרוצה לתכנן חביתה משבץ אותה כארוחה.

**שני מצבי כשל, ולא אחד.** מצרך בלי ערכי תזונה וכמות שאי אפשר להמיר
נראים זהים למשתמש ודורשים תיקון הפוך. הגרסה הראשונה אמרה "אין ערכי
תזונה" על שניהם, ובכך שלחה לערוך יוגורט שערכיו תקינים — מה שחסר לו
היה משקל ליחידה. לכן `ingredientMacros` מחזיר `reason`, והשורה אומרת
"להזין בגרם" כשזו הבעיה.

### סימון הקנייה נשמר לפי מצרך, לא לפי כמות

שינוי בתוכנית באמצע הקנייה מעדכן את הכמות בשורה אבל לא מוחק את מה שכבר
בעגלה. גלגול שבוע מאפס את הסימונים; את המזווה הוא לא נוגע.

### חלוקת העבודה בין המסכים

המתכנן השבועי קובע *מה* אוכלים. מסך היום קובע כמה מנות, מי אוכל, ומסמן
שזה קרה. בלי החלוקה כרטיס יום היה נושא שלושה סטים של פקדים והמסך היה
מפסיק להיות סריק.

### נתוני משתמש לא נדרסים לעולם

JSON פגום מגובה לפני שנטען מצב התחלתי (ואם הגיבוי נכשל — לא כותבים
בכלל). `schema_version` עתידי נועל את הכתיבה לכל אורך הסשן. חסימת
`localStorage` נופלת לזיכרון עם אזהרה כנה במקום להפיל את האפליקציה.

## עיצוב

**טיפוגרפיה:** `TelAviv Brutalist` לתצוגה, `Alef` לגוף. שניהם כבר היו
ב-`fonts/` ולא היו בשימוש בשום מקום באתר — אין בקשת רשת חיצונית.
ארבעה גדלים בלבד: meta / body / title, ועוד אחד לשם המנה בכרטיס היום.

**הכלל שמכתיב את כל השאר:** מילוי מלא הוא מטבע נדיר, ושמור לפעולה
*אחת* שצריך לעשות עכשיו. מה שהושלם מקבל קו וגוון רך. גרסה קודמת ציירה
"בישלנו" כמלבן ירוק כהה, והתוצאה הייתה ש*ביצוע* נקרא כמשקל — מוסדי,
לא ביתי. אם החרס מופיע פעמיים במסך אחד, אחד מהם טעות.

**פלטה** — אריח מטבח ישראלי:

| טוקן | ערך | שימוש |
|---|---|---|
| `--bg` | `#f7f7f4` | לבן-זיגוג. קר מקרם בכוונה |
| `--ink` | `#1e2430` | שחור כחלחל |
| `--accent` | `#2e5c8a` | קובלט — "היום", "נבחר", "הושלם" |
| `--action` | `#c4553a` | חרס — **המילוי המלא היחיד** |
| `--attn-*` | צהוב | **רק** כשל אמיתי, לא סטייה |

הכחול נבחר גם מבנית: הוא קר ובהיר, ולכן אינו נהפך לגוש כהה כשממלאים
בו שטח. כל זוג צבע/רקע נמדד — טקסט ≥4.5:1, פקדים ≥3:1, בשני המצבים.

**מצב כהה** מולחן ביד ולא היפוך מכני: המשטחים מוגבהים כלפי מעלה
(`--bg` הכהה ביותר, `--surface` בהיר ממנו), והמבטאים הובהרו.

**שני גוונים לנימוק, בלי צבע שלישי.** הצהוב (`--attn`) פסול כאן לפי
הגדרתו — הוא שמור לכשל אמיתי, ו"בישלתם אתמול" היא הסתייגות ולא שגיאה.
לכן קובלט למה שמושך ו-`--ink-soft` למה שמסתייג. הגרסה הראשונה הבדילה
ביניהם בצבע בלבד, וזה נכשל: שני הטוקנים יושבים כמעט על אותה בהירות
(6.4:1 ו-6.2:1 על לבן) ונבדלים בגוון בלבד. **המשקל** הוא שעושה את
ההפרדה בפועל, בערוץ שאינו תלוי בצבע. נופל מזה דבר שלא תוכנן והוא נכון:
מנה שכל נימוקיה אפורים נקראת מיד כמנה שאף סיבה לא מושכת אליה.

**האלמנט החתום** הוא פס השבוע: מצב היום *הוא* הצורה, לא תווית לידה —
מקווקו = לא תוכנן, מסגרת = מתוכנן, אריח רך עם וי = בישלנו, אלכסון =
אכלנו בחוץ, קו מוחק = דילגנו. הרצף אינו תג נפרד אלא הריצה של האריחים
שהושלמו. הוי אינו קישוט: בלעדיו "בישלנו" ו"מתוכנן" נבדלו רק בגוון רקע
חיוור, וזה נכשל בדיוק במבחן שהפס קיים בשבילו.

### תהליך העבודה על עיצוב

מוגדר ב-`CLAUDE.md` תחת "עבודת עיצוב": סקיל `frontend-design` לכיוון
לפני כתיבת CSS, ו-`/design:ux-copy`, `/design:critique`,
`/design:accessibility` בשלבים שאחריו.

שלושת הדברים שלמעלה — הפלטה, הטיפוגרפיה, ופס השבוע — הם **החלטות
מוכרעות**. הסקילים מעדנים בתוכן ולא מתחילים מהן מחדש.

**פערים אמיתיים:**

- **אין אונבורדינג.** המחקר ממליץ על 5-7 שאלות פתיחה (גודל משק בית,

  ו"בן/בת הזוג". אפשר לערוך אותם במסך המאקרו, אבל צריך לדעת ללכת לשם.
- **אין תמונות מנה.** השוק הוא photography-first; זה הפער הוויזואלי
  הגדול שנותר.

**נדחה במודע:**

- סנכרון בין מכשירים (דורש שרת — משנה את כל אופי המוצר)
- הפחתה אוטומטית מהמזווה (ראה למעלה)
- `dislikes` בפרופיל קיים במודל ואף אחד לא קורא אותו — והוא המועמד
  הטבעי הבא למנוע ההצעות: אות פסילה, לא שקלול
- `tags` על מנה נשמר ומנורמל, ואף אחד לא קורא אותו
- `macros_override` על מנה נתמך במנוע ונשמר בעריכה, אבל אין ממשק
  שקובע אותו (המקרה האמיתי: יודעים קלוריות של מנה במסעדה ולא את הפירוק)
