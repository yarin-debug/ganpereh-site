# מתכנן הארוחות

אפליקציית ווב פרטית לתכנון ארוחות במשק בית. מובייל-תחילה, עברית RTL.
כל המצב יושב ב-`localStorage` של המכשיר, ו-`localStorage` נשאר הבעלים
גם כשהסנכרון פעיל.

בלי build ובלי תלויות — ES modules טהורים. סנכרון בין מכשירים קיים
כשכבה נפרדת (`js/sync/`), ומדברת עם Supabase ב-`fetch` רגיל בלי SDK.
**כרגע היא רדומה ולא מבצעת שום בקשת רשת** — לא מפני שהיא לא מוגדרת,
אלא מפני שאין סשן: מסך ההתחברות טרם נבנה. הפירוט תחת "סנכרון בין
מכשירים".

---

## המסכים

| טאב | מה הוא עונה עליו |
|---|---|
| **היום** | "מה אוכלים עכשיו" + סימון שזה קרה. טאב ברירת המחדל. |
| **השבוע** | תכנון: מה מרכיבים בכל משבצת, ואילו ארוחות בכלל מתכננים. |
| **קניות** | מה לקנות, מקובץ למדפי סופר, עם סימון בעגלה. עובד אופליין. |
| **מזווה** | מה כבר בבית. מקוזז אוטומטית מרשימת הקניות. |
| **מאקרו** | מה נאכל בפועל מול היעדים, לכל פרופיל. מתאר, לא שופט. |

## מפת המודולים

**לוגיקה טהורה** — בלי DOM, בלי גישה ל-store, נבדקת ישירות:

| קובץ | אחריות |
|---|---|
| `normalize.js` | המרות יחידות, סכימת רשימת קניות, חישוב מאקרו |
| `plan.js` | ארוחות, מצב יום, רצף בישול, מפתחות שורות קנייה |
| `compose.js` | תפקידי רכיבים, קריאת הרכבת המשבצת וכתיבתה, סדר וסיכום |
| `pantry.js` | קיזוז המזווה מול דרישות השבוע |
| `catalog.js` | מיזוג מנות/מצרכי זרע עם עריכות המשתמש |
| `profiles.js` | מי במשק הבית, יעדים, וניקוי משבצות בהוצאת אדם |
| `history.js` | מתי בישלנו מה, והעתקת שבוע קודם |
| `suggest.js` | דירוג מנות למשבצת ריקה, והנימוק לכל הצעה |
| `extras.js` | נשנושים ומשקאות — מאקרו, קנייה, והוספה מהירה |
| `backup.js` | עטיפת קובץ הגיבוי, אימות קובץ נכנס, וספירת מה יש בו |
| `share.js` | רשימת הקניות כטקסט להדבקה |
| `images.js` | דחיסת תמונות מנה ואחסונן ב-IndexedDB |

**מצב ונתונים:**

| קובץ | אחריות |
|---|---|
| `store.js` | התמדה, נרמול קלט פגום, גלגול שבוע, סנכרון בין טאבים |
| `data.js` | נתוני זרע — מנות, מצרכים, מדפים. **בקוד, לא באחסון.** |

**סנכרון** (`js/sync/`) — שכבה נפרדת, מוגדרת אך רדומה עד ההתחברות הראשונה:

| קובץ | אחריות |
|---|---|
| `config.js` | כתובת הפרויקט והמפתח — **מלאים**. ריק = כבוי, אבל הוא לא ריק. **פרויקט נפרד מהדשבורד.** |
| `entities.js` | פירוק המצב לשורות, טביעות, מיזוג. לוגיקה טהורה, נבדקת |
| `auth.js` | קישור קסם למייל, סשן, רענון אסימון |
| `rest.js` | קריאות PostgREST — משק בית, הזמנות, משיכה ודחיפה |
| `sync.js` | סדר הפעולות, השהיה, מצב לתצוגה |

**ממשק** — `app.js` (רישום מסכים), `ui-today/week/list/pantry/score.js`
(מסכים), `ui-overlay.js` (מחסנית שכבות ולבני טופס), `ui-sheet.js` (בורר
ההרכבה), `ui-dish-editor.js` / `ui-ingredient-editor.js` / `ui-profiles.js`
(טפסים), `ui-strip.js` (פס השבוע), `ui-onboarding.js` (מסך הפתיחה),
`ui-tour.js` (התדריך הראשוני), `ui-backup.js` (הורדת גיבוי וטעינה
ממנו), `ui-suggest.js` (שכבת אישור ההצעות), `ui-extras.js` (נשנושים
במסך היום).

**מסך הפתיחה והתדריך הם שני דברים, ולכן שני מפתחות.** הראשון בונה את
*משק הבית* ונשמר במצב (`onboarded`), כלומר יסתנכרן כשהסנכרון יידלק.
השני מלמד את *הממשק* ולכן הוא דגל מקומי במכשיר (`gp_meals_tour_seen`):
לבן זוג שיצטרף למשק בית קיים התשובה ל"כבר ראית איך זה עובד" היא לא,
גם כשמסך הפתיחה כבר נענה.

**זרימה חד-כיוונית:** המסכים קוראים מה-store וכותבים דרך `store.update`
בלבד. `app.js` מחזיק את המנוי היחיד שמרנדר מחדש. אף מסך לא מייבא בחזרה
מ-`app.js` — אין מעגל תלויות.

## מודל הנתונים

```js
{
  schema_version: 1,
  plan: {
    week_start: "2026-07-26",          // תמיד יום ראשון
    slots: {
      "2026-07-28.dinner": {            // מפתח: תאריך.ארוחה
        dish_id: "dish.schnitzel",      // הרכיב הראשי
        extras: ["dish.oven_chips", "dish.israeli_salad"],
        servings: 2,                    // אחד לכל הרכיבים — צלחת, לא ארוחות נפרדות
        eaters: ["p1", "p2"],
        status: "planned"               // planned | cooked | ate_out | skipped
      }
    },
    extras: {                           // נשנושים ומשקאות, רשימה ליום
      "2026-07-28": [{
        id: "x1",
        ingredient_id: "ing.coffee_black",
        qty: 1, unit: "unit",
        kind: "snack",                  // snack | drink
        eaters: ["p1"],
        planned: false, eaten: true     // שתי עובדות, לא ציר אחד
      }]
    },
    checked: { "ing.onion": true }      // סימוני קנייה, מתאפסים בגלגול שבוע
  },
  profiles: [{ id, name_he, targets: { kcal, protein_g, fat_g, carbs_g }, dislikes: [], archived }],
  pantry:      { "ing.onion": { qty: 300, unit: "g" } },
  dishes:      { "dish.u1": { role: "side", ... } },  // מנות משתמש + עריכות של זרע
  ingredients: { "ing.u1": { ... } },   // מצרכי משתמש
  prefs:       { meals: ["breakfast", "dinner"] },  // אילו ארוחות מתכננים
  onboarded:   true                     // האם מסך הפתיחה הושלם
}
```

### רכיבים ותפקידים

לכל מנה `role` — `main` (מנה שלמה), `protein`, `side`, `veg`, `dip` —
והוא קובע לאיזו קבוצה היא נכנסת בבורר ההרכבה ובאיזה סדר היא נקראת
בתוך ארוחה. מנה בלי `role` מוכר היא `main`, וזה מה שכל המנות היו לפני
שהתפקידים קיימים.

משבצת מחזיקה רכיב ראשי (`dish_id`) ותוספות (`extras`). כל מה שהמנוע
עושה — רשימת קניות, מאקרו, היסטוריית בישול, העתקת שבוע — עובר על כל
הרכיבים, לא רק על הראשי.

> ⚠️ **שני שדות בשם `extras`, ואין ביניהם שום קשר.**
> `slot.extras` הוא **מזהי מנות** — הרכיבים הנוספים בצלחת, ומטופל
> ב-`compose.js`. `plan.extras` הוא **מפה מתאריך לרשימת נשנושים
> ומשקאות**, ומטופל ב-`extras.js`. שניהם הגיעו מקווי פיתוח שרצו
> במקביל ולא ידעו זה על זה, והשם נפגש רק במיזוג. הם על אובייקטים
> שונים ולכן שום דבר לא נשבר — אבל קוד שמקבל "extras" בלי הקשר הוא
> מלכודת, ובדיקה חדשה צריכה לומר במפורש על איזה מהם היא מדברת.

### מדיניות סכמה

`SCHEMA_VERSION` הוא **1** ולא עלה מאז. כל התוספות עד היום היו נקיות —
שדות חדשים בלבד. `coerceState` פורס את ה-raw ושומר שדות שהגרסה הזו לא
מכירה, כך שגרסה ישנה במטמון לא מוחקת נתונים של גרסה חדשה.

להעלות את הגרסה **רק** כששינוי אינו תואם אחורה. הערך מנעילת כתיבה
(`schema_version` עתידי → האפליקציה לא כותבת בכלל) גדול מהערך של מספור
מסודר.

## החלטות שקל להפוך בטעות

הרשימה הזו קיימת כדי שהחלטה נכונה לא תתהפך בסיבוב הבא. כל אחת מהן
מתועדת גם בראש הקובץ הרלוונטי.

### הרכבה חיה בתוך הסכמה הקיימת, ולא במערך שמחליף את `dish_id`

הצורה הנקייה הייתה `components: [...]` במקום `dish_id`. היא נפסלה:
`coerceSlots` — **בכל גרסה של האפליקציה, כולל גרסה ישנה שיושבת במטמון
של מכשיר אחר** — זורקת משבצת שאין בה `dish_id` מחרוזתי. מעבר למערך
בלבד היה גורם לגרסה הישנה למחוק בשקט כל ארוחה מורכבת. זו בדיוק מחיקת
נתוני המשתמש שהחוזה של `store.js` אוסר.

לכן: `dish_id` הוא הרכיב הראשי ו-`extras` השאר. גרסה ישנה תציג רק את
הראשי ותשמור את `extras` כמו שהוא דרך פריסת השדות — כלומר תפסיד תצוגה,
לא נתונים. יש בדיקה שמאמתת שתנאי הקבלה הזה עדיין קיים.

**הסדר נגזר ולא נשמר.** הוא מגיע מהתפקיד, ולכן שינוי תפקיד של מנה
בעורך מסדר מחדש כל משבצת שמצביעה עליה בלי הגירה. מנה שאי אפשר לפתור
יורדת לסוף ואינה מקבלת את דירוג "מנה שלמה" — אחרת מזהה שבור היה קופץ
לראש ההרכבה, נשמר כ-`dish_id`, ומופיע בכרטיס היום בגודל מלא כ"מנה לא
מוכרת" במקום המנה שבאמת נבחרה.

**`servings` אחד לכל הרכיבים.** צלחת אחת עם שני מרכיבים, לא שתי ארוחות
נפרדות. כמות פר-רכיב ("שניצל למנה אחת אבל אורז לשתיים") נדחתה בכוונה:
היא מכפילה את הפקדים בכרטיס היום בשביל מקרה קצה.

### זמן ההרכבה הוא המרבי, לא הסכום

השניצל מטגן בזמן שהאורז על האש. סכימה הייתה מציגה 75 דקות לארוחה
שלוקחת 40, ומספר שמנפח את המאמץ הוא בדיוק מה שגורם לא לבשל. המרבי אינו
מדויק לגמרי — יש רכיבים שבאמת מתווספים — אבל הוא הקירוב הישר היחיד
מתוך המידע שיש.

### אין המרה מנוחשת — בשום מקום

`toBase` מחזיר כמות **מסומנת** כשאי אפשר להמיר, לא שגיאה ולא אפס שקט.
"גביע יוגורט אחד" בלי `unit_weight_g` מגיע לרשימת הקניות כפריט "לבדוק
ידנית" עם הכמות המקורית. אותו כלל בדיוק חל על קיזוז המזווה.

מספר מומצא ברשימת קניות גרוע ממספר חסר — הראשון נראה כמו ידיעה.

### מנות זרע נשארות בקוד; עריכה כותבת העתק

הפיתוי: להעתיק את כל הזרע ל-`localStorage` בטעינה הראשונה ומשם לערוך.
המחיר: תיקון בנתוני זרע (ערך תזונתי שגוי, שם, זמן הכנה) לעולם לא מגיע
למי שכבר פתח את האפליקציה פעם אחת.

לכן `catalog.js` ממזג: הזרע בקוד, עריכה שומרת העתק תחת אותו מזהה,
ההעתק גובר. מחיקת ההעתק היא "שחזור לגרסה המקורית" וקיימת בממשק.

### ארכיון, לא מחיקה — למנות ולאנשים כאחד

משבצות מצביעות על מנה לפי מזהה ושורדות שבועות אחורה. מחיקה הייתה הופכת
כל היסטוריה שמצביעה עליה ל"מנה לא מוכרת" — כולל מסך המאקרו של שבועות
שכבר נאכלו. מנה בארכיון יורדת מהבורר וממשיכה להיפתר בכל מקום אחר.

**אותו נימוק לפרופילים, ובחדות אף גדולה יותר:** `slot.eaters` מחזיק
מזהי אנשים, וחישוב המאקרו מחלק את המנות במספרם. מחיקת פרופיל הייתה
משאירה מזהה יתום בתוך `eaters`, והמחלק היה ממשיך לספור אדם שכבר לא
קיים — כלומר להציג לכל השאר **פחות ממה שהם באמת אכלו**.

הוצאת אדם ממשק הבית מנקה את `eaters` **מהשבוע הנוכחי והלאה בלבד**.
שבועות שעברו נשארים כמו שהם, כי המאקרו שלהם היה נכון כשהוא נאכל.
משבצת שהוא היה האוכל היחיד בה נמחקת — להשאיר אותה עם `eaters` ריק היה
גרוע יותר, כי `coerceSlots` ממלא רשימה ריקה במשק הבית הנוכחי והמנה
הייתה מוקצית בשקט למישהו אחר.

### המזווה לא מתעדכן לבד אחרי "בישלתי"

הפיתוי מובן — סימון הבישול כבר קיים. אבל האפליקציה יודעת כמה המתכון
*נוקב*, לא כמה נכנס לסיר ולא אם נשאר חצי בצל. מלאי שמחסיר מספרים שלא
קרו מצטבר לשקר, והשקר מתבטא במקום הגרוע ביותר: רשימת קניות שמחסירה
פריט שאין בבית.

מזווה ידני שגוי הוא באחריות מי שהקליד. מזווה שמחסיר לבד שגוי בשקט.

### מצרך בלי ערכי תזונה הוא מצב תקין

הדרישה היחידה ליצירת מצרך היא שם. בלי `nutrition_per_100` המנה מסומנת
"חלקי", ובלי `unit_weight_g` היא נופלת למסלול הידני — שני מסלולים
שנבדקים. לחייב ארבעה ערכים כדי להוסיף "פטרוזיליה" היה גורם לאנשים
להמציא מספרים, וזה בדיוק מה שהמנוע נועד למנוע.

ערכים חלקיים (קלוריות וחלבון בלבד) נשמרים חלקיים ומסמנים את המנה
כחלקית — לא מושלמים באפס.

### הריבוע בפס השבוע מתמלא רק כשהיום סגור

כל עוד יש ארוחה מתוכננת שלא הוכרעה, היום "מתוכנן" — גם אם כבר בישלת
בבוקר. אחרת גובר מה שקרה בפועל: בישלנו ← בחוץ ← דילגנו.

**הרצף שואל שאלה אחרת** — "בישלת בבית לפחות ארוחה אחת?" ולא "סגרת את
היום?". ארוחת בוקר מבושלת בזמן שהערב פתוח לא שוברת רצף באמצע היום.
ולהיום יש ארכה: בשש בערב עוד לא בישלת, וזה לא מאפס רצף של שבועיים.

### `onboarded` — אותו שדה, שתי ברירות מחדל

`defaultState` מחזיר `onboarded: false`, ולכן התקנה טרייה עוברת דרך מסך
הפתיחה. `coerceState`, שרץ **רק על בלוב שכבר קיים במכשיר**, מחזיר `true`
כשהשדה חסר.

זה נראה כמו חוסר עקביות והוא הלב של הפיצ'ר: בלוב שנשמר לפני שמסך הפתיחה
נולד שייך בהגדרה למי שכבר עובד עם האפליקציה. לשלוח אותו להגדרה מחדש היה
מציע לו לבנות משק בית שכבר קיים לו, מעל תוכנית שכבר תוכננה — והמסך
מסיים בכתיבה שדורסת את `profiles`. רק `false` מפורש, כלומר מי שפתח את
המסך ולא סיים אותו, מחזיר לשם.

`needsOnboarding()` מכבה את המסך כשכתיבה ממילא תיכשל (סכמה עתידית, או
JSON פגום שלא הצליח להתגבות). מסך שמבקש להגדיר משק בית ואז לא שומר אותו
הוא הבטחה ריקה. אחסון חסום דווקא כן מקבל אותו — שם הסשן הזה עובד,
וההודעה בראש המסך כבר אומרת שהוא לא יישמר.

### ארוחה שכבר תוכננה מוצגת גם כשהיא מחוץ להעדפה

`prefs.meals` הוא סינון **תצוגה** בלבד. `dayState` והרצף מסננים ארוחות
ריקות ממילא, ולכן ארוחה שלא מתכננים פשוט אינה קיימת בעיניהם — אין צורך
לשנות בהם דבר.

אבל ארוחה שכבר יש בה משבצת מוצגת תמיד, גם אחרי שהורידו אותה מההעדפה.
הסתרה שלה הייתה יוצרת נתונים בלתי נראים: המנה ממשיכה להיספר במצב היום,
ברשימת הקניות ובמאקרו, ולמשתמש אין שום מסך שבו הוא יכול לגעת בה. זה
בדיוק הכלל של מצרך לא מזוהה שמוצג ברשימה במקום להישמט בשקט.

ההעדפה ניתנת לשינוי במסך השבוע. בלי זה היא הייתה דלת חד-כיוונית.

### התמונות אינן ב-store, ואינן בקובץ הגיבוי

כל שאר המצב יושב ב-`localStorage`, ולתמונות זה פשוט לא עובד: המכסה היא
כ-5MB, האחסון הוא מחרוזות בלבד (כלומר base64, שמנפח ב-33%), והגישה
סינכרונית וחוסמת רינדור. תמונה אחת מהטלפון היא 3-5MB לפני דחיסה —
כלומר **תמונה אחת הייתה מפילה את כל הנתונים**, כולל התוכנית והמזווה.
לכן IndexedDB, שמחזיק `Blob` כמו שהוא.

הדחיסה קורית **לפני** השמירה ולא בהצגה, מאותה סיבה: לשמור את המקור
פירושו למלא את המכסה בשלוש תמונות ואז להיכשל בשקט על הרביעית. הצלע
הארוכה מוגבלת ל-900 (מספיק לרוחב טלפון בצפיפות 2x) ו-JPEG ב-0.75.
בפועל: 1600×1200 נכנסה כ-7KB.

**קובץ הגיבוי אינו כולל תמונות**, וזה נאמר במפורש בטקסט שליד הכפתור.
base64 של עשר תמונות היה קובץ במגהבייטים שאי אפשר לשלוח בהודעה — וזו
כל המטרה של הגיבוי. גיבוי שמבטיח "הכל" ומחזיר תוכנית בלי תמונות הוא
בדיוק סוג ההפתעה שהמנגנון נבנה כדי למנוע.

### התמונה נכתבת לפני המנה, לא אחריה

`store.update` מודיע למאזינים באופן סינכרוני, וכל המסכים מתרנדרים בתוך
הקריאה. כשהתמונה נכתבה *אחרי* הכתיבה למצב, הרינדור קרה כשהיא עוד לא
הייתה במסד — כלומר שומרים תמונה, וכרטיס היום נשאר בלי שינוי עד הרענון
הבא. המזהה נגזר מראש (`nextDishId` טהורה), ולכן אפשר לכתוב לפי אותו
מפתח לפני הכתיבה למצב.

כשל בכתיבת התמונה אינו מבטל את שמירת המנה: ההודעה אומרת "המנה נשמרה,
אבל התמונה לא נכנסה". להחזיר "השמירה נכשלה" על מנה ששמורה היה שולח
את המשתמש להקליד הכל מחדש בחינם.

### "לא אוהב" הוא סימון ולא חסימה

`dislikes` היה שדה מת: קיים במודל, מנורמל בכל טעינה, ואף מסך לא קרא
אותו. הפיתוי בחיווט שלו הוא להסתיר את המנה מהבורר — וזו בדיוק אותה
טעות של מצרך לא מזוהה שנשמט בשקט. אדם לא אוכל בבית כל ערב, ומנה
שהוסתרה היא מנה שאי אפשר לתכנן גם כשהוא לא כאן.

לכן: המנה נשארת בבורר, מקבלת את משטח `--sunken` והערה בשורה שכבר
קיימת. **מה שכן משתנה הוא ההצעות** — היא יורדת מ"לא בישלנו מזמן", כי
הצעה היא המלצה, והמלצה על משהו שמישהו לא אוכל היא הרעש שההצעות נועדו
לא להיות.

הסימון נקבע **בעורך המנה** ולא במסך הפרופיל, למרות שהוא נשמר על
הפרופיל. בעורך כבר מסתכלים על המנה; במסך הפרופיל היה צריך לבחור אותה
מתוך רשימה של עשרות.

**התווית מסכימה עם המנה ולא עם האדם.** "דנה לא אוהבת" היה גוזר מגדר
משם — נתון שאין לאפליקציה ושאין סיבה לבקש. "לא אהובה על דנה" מסכים עם
*המנה*, שהיא נקבה, ולכן הוא נכון לכל אדם.

ו-`setDislikes` **לא נוגעת בפרופיל בארכיון**: הטופס מציג רק את מי
שבמשק הבית, ולגזור מרשימת המסומנים "הוא לא סומן, אז למחוק" היה מוחק
בשקט נתון שהמשתמש מעולם לא ראה. זו בדיוק ההעדפה שצריכה לשרוד עד
שהוא יחזור.

### דריסת מאקרו — שדה ריק אינו אפס, גם בתצוגה

`macros_override` נתמך במנוע מההתחלה ואף מסך לא קבע אותו. המקרה
האמיתי: מנה שיודעים עליה מספר אחד ולא את הפירוק — מנה מהמסעדה, או
מתכון של מישהו אחר. בלי המסלול הזה הדרך היחידה להזין אותה הייתה להמציא
רשימת מצרכים, וזו ההמצאה שכל המנוע נבנה כדי למנוע.

`coerceMacroOverride` מבחינה בין *ריק* לבין *מספר*, ולא בין אפס לבין
לא-אפס: יש מנות בלי שומן, ולפסול אפס היה מכריח להקליד 0.1. טופס שכולו
ריק מחזיר `null` — אין דריסה, ולא אובייקט של ארבעה אפסים.

**והתצוגה חייבת לומר את אותו דבר שהסימון אומר.** `dishMacros` ממלא
שדה חסר באפס ומסמן `partial` בדיוק כדי שלא ייקרא כידע — אבל הגרסה
הראשונה של המסך הדפיסה בכל זאת "0 גרם חלבון", כלומר "אין במנה הזו
חלבון". הסימון לא שווה כלום כשהמספר לידו סותר אותו. שדה שלא הוזן
מוצג "—".

מי גובר על מי נאמר **במילים** מתחת למספר, לא בצבע — אותו נימוק בדיוק
של טבלת ההשוואה בייבוא.

### מוצעות רק מנות שכבר בושלו, ורק כשיש ממה לקצר

הפיתוי ב"לא בישלנו מזמן" הוא לדחוף לרשימה גם מנות שמעולם לא בושלו, כדי
שתמיד יהיה מה להציע. הכותרת פשוט אינה נכונה עליהן — וזו אותה משפחה של
שקר קטן שהמנוע נמנע ממנה בכל מקום אחר. מנה שבישלו פעם היא גם המלצה
חזקה יותר: משק הבית כבר הצביע עליה. כשאין מה להציע מחזירים רשימה ריקה
והממשק לא מציג כלום.

הסף הוא **שבועיים**: מנה שבושלה לפני ארבעה ימים אינה "מזמן", וסף נמוך
מדי הופך את ההצעה לרעש שמפסיקים להסתכל עליו. מנה שכבר בתוכנית השבוע
מסוננת — להציע אותה שוב זו בעצמה עייפות תפריט.

והבלוק כולו מוסתר כשבקטלוג פחות משבע מנות: שם ההצעות *הן* הקטלוג,
והן חוזרות מילה במילה על מה שנמצא שורה מתחתיהן, כולל תווית
ה"בישלתם לפני..." שכבר יושבת בכל שורה. הקיצור קיים כדי לחסוך גלילה,
ורשימה שנכנסת למסך אחד אינה דורשת קיצור.

### הייבוא הוא הפעולה היחידה שמוחקת נתונים בכוונה — ולכן גם היא מגבה

כל שאר המנגנון ב-`store.js` מגן מפני *האפליקציה*. הוא לא מגן מפני
הדפדפן: ניקוי נתוני גלישה, פינוי אחסון בספארי או מכשיר חדש מוחקים הכל,
ואין שרת. הקובץ הוא הדרך היחידה להוציא נתונים מהמכשיר, ולכן הוא קיים.

הכיוון המסוכן הוא הייבוא, והוא מציית לאותו כלל של ה-JSON הפגום:
הבלוב הקיים מוצנע תחת `__before_import` **לפני** הכתיבה, ואם ההצנעה
נכשלה — הייבוא לא קורה בכלל. גם כאן המקום הראשון לא נדרס, כך שמי
שייבא פעמיים בטעות מוצא תחת המפתח הראשון את הנתונים האמיתיים שלו ולא
את תוצאת הטעות הקודמת. כתיבה שנכשלה מחזירה את המצב הקודם לזיכרון,
אחרת המסך היה מציג נתונים מיובאים שאינם שמורים בשום מקום.

`readBackup` מקבל **שתי צורות**: את העטיפה שהאפליקציה כותבת, וגם בלוב
מצב חשוף. מי שהעתיק את הערך היישר מ-`localStorage` כדי להציל נתונים
מדפדפן שנתקע מחזיק ביד בדיוק את הצורה השנייה, ולדחות אותו היה לדחות
אותו ברגע שהוא הכי צריך את זה. גיבוי מסכמה **עתידית** נדחה — אותו
נימוק כמו נעילת הכתיבה: עדיף לסרב מאשר לקצץ שדות בשקט.

### מה שמצטמצם בייבוא נאמר במילים, לא בצבע

הגרסה הראשונה של טבלת ההשוואה צבעה בחרס כל מספר שקטן מהקיים. שתי
בעיות: חרס כטקסט נמדד 4.26 ואינו עובר את הסף, וצבע לבדו ממילא אינו
סימן — קורא מסך היה מקבל טבלה של מספרים שווי משקל. משפט אחד מתחת
לטבלה אומר את זה לכולם, ואומר יותר: לא רק *ש*משהו קטן, אלא *מה*.

באותו נימוק, מכשיר שעוד לא הוגדר מקבל טבלה בעמודה אחת. עמודת "עכשיו"
שם הייתה מציגה "2 אנשים" — פרופילי הזרע הבלתי נראים שאיש לא הזין —
ומבטיחה למשתמש שהוא עומד לאבד משהו שאין לו.
### הצעה נושאת נימוק, ולעולם לא נכתבת לבד

ציון התאמה ("87%") היה בדיוק המספר המומצא שכל המנוע נועד לא לייצר: הוא
נראה כמו ידיעה ואי אפשר לחלוק עליו. לכן כל הצעה מחזירה `reasons`
בעברית, וכל אות דירוג שמזיזה את הסדר גם אומרת את עצמה במילים. אות
שאין לה מה לומר לא משפיעה על הדירוג.

**וכלום לא נכתב בלי אישור.** הכפתור יכול היה למלא את כל המשבצות
הריקות בלחיצה, כמו "העתקה משבוע שעבר" — אבל ההעתקה מחזירה החלטות
שהמשתמש כבר קיבל, וההצעה מייצרת החלטות שלא קיבל מעולם. מילוי שקט של
21 משבצות מצטבר לתפריט שאיש לא בחר, והוא מתגלה בסופר. אותו נימוק
בדיוק כמו המזווה שלא מתעדכן לבד אחרי "בישלתי".

שלוש עדינויות שהתגלו רק בבנייה, וכל אחת נעולה בבדיקה:

- **קנס החזרה מוכפל ולא רווי.** גרסה שנתנה −8 לשתי הופעות ועצרה שם
  הנחיתה את כל המנות על אותה רצפה ברגע שכולן הגיעו לשתיים; שובר
  השוויון לפי שם הכריע תמיד לאותו צד, ואותה מנה הוצעה 16 פעם ברצף.
- **ההיסטוריה והחזרה חולקות את ציר הזמן ולא חופפות.** משבצת שכבר
  בושלה אינה נספרת כ"חזרה", אחרת מנה שבושלה אתמול קיבלה עונש כפול
  והציגה שני נימוקים לעובדה אחת — "בישלתם אתמול · כבר בתפריט השבוע".
- **אותה מנה לא מוצעת פעמיים באותו יום.** זו הפסילה היחידה במנוע ולא
  שקלול, כי קנס לבדו לא מנע אותה: כיסוי מזווה מלא גבר עליו. היא נסוגה
  כשאין ממה לבחור — ספרייה קטנה משלוש ארוחות תקבל חזרה ביום, וזו עדיין
  תשובה טובה יותר ממשבצת ריקה בלי הצעה.

**הכיסוי נמדד מול המזווה כפי שהוא רשום**, בלי לנכות את מה שכבר תפוס
בשביל שאר השבוע. לכן הנוסח הוא "כל המצרכים במזווה" — אמירה על המלאי,
שהיא נכונה — ולא "אין מה לקנות", שהיא הבטחה. רשימת הקניות נשארת
הסמכות היחידה על מה חסר.

### נשנוש הוא שתי עובדות, לא סטטוס אחד

`planned` ו-`eaten` נראים כמו שני מצבים על ציר אחד, אבל הם בלתי תלויים
וכל אחד מזין מסך אחר:

| planned | eaten | מה זה | לאן זה נכנס |
|---|---|---|---|
| ✓ | | בתוכנית, טרם נאכל | רשימת הקניות |
| ✓ | ✓ | תוכנן ונאכל | קניות **וגם** מאקרו |
| | ✓ | נשנוש שקרה | מאקרו בלבד |

סטטוס יחיד היה מאבד את ההבחנה בין "אכלתי תפוח שתכננתי" לבין "אכלתי
עוגייה אצל חברים" — והראשון צריך להופיע ברשימת הקניות בעוד השני לא
אמור להופיע בה לעולם. מתוכנן שכבר נאכל **נשאר** ברשימה, מאותו היגיון
שמשבצת מסומנת "בישלנו" נשארת בה: קונים לפני, לא אחרי.

**המקטע הזה נמדד בחיכוך של שנייה אחת.** נשנוש מוזן עשרות פעמים בשבוע,
וכל הזנה מתחרה מול "לא בא לי עכשיו". לכן המסלול הראשי הוא צ'יפ בהקשה
אחת, מדורג לפי מה שבאמת חוזר, והשכבה קיימת למה שהצ'יפים לא מכסים —
לא להפך. בורר שדורש חיפוש, כמות ובחירת אדם יינטש אחרי יומיים.

**התוספות מצביעות על מצרך ולא על מנה.** נשנוש הוא כמעט תמיד פריט אחד,
ותמיכה במנות הייתה מכפילה כל מסלול (מאקרו, קנייה, בורר) בשביל מקרה
שכבר יש לו בית: מי שרוצה לתכנן חביתה משבץ אותה כארוחה.

**שני מצבי כשל, ולא אחד.** מצרך בלי ערכי תזונה וכמות שאי אפשר להמיר
נראים זהים למשתמש ודורשים תיקון הפוך. הגרסה הראשונה אמרה "אין ערכי
תזונה" על שניהם, ובכך שלחה לערוך יוגורט שערכיו תקינים — מה שחסר לו
היה משקל ליחידה. לכן `ingredientMacros` מחזיר `reason`, והשורה אומרת
"להזין בגרם" כשזו הבעיה.

### סימון הקנייה נשמר לפי מצרך, לא לפי כמות

שינוי בתוכנית באמצע הקנייה מעדכן את הכמות בשורה אבל לא מוחק את מה שכבר
בעגלה. גלגול שבוע מאפס את הסימונים; את המזווה הוא לא נוגע.

### חלוקת העבודה בין המסכים

המתכנן השבועי קובע *מה* אוכלים. מסך היום קובע כמה מנות, מי אוכל, ומסמן
שזה קרה. בלי החלוקה כרטיס יום היה נושא שלושה סטים של פקדים והמסך היה
מפסיק להיות סריק.

### נתוני משתמש לא נדרסים לעולם

JSON פגום מגובה לפני שנטען מצב התחלתי (ואם הגיבוי נכשל — לא כותבים
בכלל). `schema_version` עתידי נועל את הכתיבה לכל אורך הסשן. חסימת
`localStorage` נופלת לזיכרון עם אזהרה כנה במקום להפיל את האפליקציה.

## סנכרון בין מכשירים (`js/sync/`)

### ⚠️ שני שערים, וכרגע רק השני סגור

התיעוד הזה הבטיח פעם ש"כל עוד `config.js` ריק — אין מאזינים, אין
טיימרים, אין בקשות רשת". **ההבטחה כבר לא מתארת את המצב**, והחלפת
ההבטחה בלי הסבר הייתה מוחקת בדיוק את מה שצריך לדעת כאן:

| שער | מה בודק | מצבו היום |
|---|---|---|
| `syncConfigured()` | האם יש כתובת פרויקט ומפתח | **פתוח** — `config.js` מלא |
| `signedIn()` | האם יש סשן מחובר | **סגור** — אין מסך התחברות |

כלומר `attachSync` **כן** רושם את המאזינים (מנוי ל-store,
`visibilitychange`, `online`). מה שמונע כל בקשת רשת הוא השער השני:
`scheduleSync` ו-`syncNow` יוצאים מיד על `signedIn()`. "אפס בקשות
רשת" נכון היום — אבל בגלל היעדר הסשן, לא בגלל התצורה.

**מה יהפוך את השכבה לפעילה:** בניית מסך ההתחברות. ההתחברות הראשונה
כותבת סשן, `signedIn()` מתחיל להחזיר true, והמאזינים שכבר רשומים
מתחילים לירות סנכרון בפועל — בלי שורת קוד נוספת ב-`config.js`. לכן
מסך ההתחברות אינו "עוד מסך": הוא המתג.

לכבות בכל זאת — לרוקן את `SUPABASE_URL`. השער הראשון עדיין עובד, והוא
עדיין הדרך המהירה לעצור הכל.

### ⚠️ פרויקט Supabase נפרד — לא סכמה, לא קידומת

זו לא העדפת סדר אלא גבול אבטחה. מדיניות ה-RLS של **הדשבורד**
(`ganpereh-dashboard`) מתירה גישה לכל מי שה-JWT שלו נושא כתובת
מרשימה קבועה, ו-`yarin@ganpereh.co.il` נמצא בה. פרויקט Supabase חותם
את כל האסימונים שלו באותו סוד — ולכן פרויקט משותף היה הופך התחברות
למתכנן הארוחות לאסימון תקף לקריאת הלידים, הצעות המחיר ופרטי חשבון
הבנק שב-CRM.

פרויקט נפרד = סוד חתימה אחר = אסימון של הארוחות פשוט לא נפרס שם.
זו ההפרדה היחידה שלא דורשת שמישהו יזכור להחזיק אותה.

הפירוט המלא, כולל בדיקת "אני בפרויקט הנכון?", בראש
`app/supabase/schema.sql`.

### האחסון המקומי נשאר הבעלים

השרת אינו מקור האמת אלא יעד סנכרון. כל קריאה וכתיבה ממשיכות לעבור
דרך `localStorage` כמו קודם, ושכבת הסנכרון רצה לצדן. רשימת הקניות
נפתחת בסופר בלי קליטה — סנכרון שהופך רשת לתנאי לקריאה היה שובר בדיוק
את התכונה שבגללה האפליקציה נבנתה כך. כישלון רשת כאן אינו מצב שגיאה
אלא מצב רגיל.

### שורה לפריט, לא הבלוב השלם

באחסון המקומי המצב הוא מחרוזת JSON אחת, וזה נכון שם: כותב אחד, כתיבה
אטומית. מול שרת עם **שני** כותבים זה נשבר — שניים בבית עורכים
במקביל, כל אחד שולח את הבלוב השלם שלו, והשני מוחק את מה שהראשון הרגע
עשה. גם כשהם נגעו בדברים שונים לגמרי.

הפירוק ל-`slot` / `checked` / `pantry` / `dish` / `ingredient` /
`profile` / `meta` הופך את זה להתנגשות שלא קיימת: כל צד שולח רק את
המפתחות שהוא שינה. "אחרון כותב מנצח" נשאר, אבל ברמת המשבצת הבודדת.

`value = null` הוא **מצבה** ולא "אין ערך". בלי זה מחיקה לא הייתה
מסתנכרנת: המכשיר השני לא היה שומע עליה ומחזיר את השורה בסבב הבא —
כלומר כל מחיקה הייתה מתבטלת מעצמה.

### סדר הפעולות הוא מה שהופך את המיזוג לנכון

1. משיכה של מה שהשתנה בשרת
2. חישוב מה השתנה מקומית מאז הסנכרון האחרון
3. החלת המשיכה — **פרט למפתחות ששונו מקומית**
4. דחיפת המקומיים

שלב 3 הוא הלב. בלעדיו משיכה שקדמה לדחיפה הייתה מבטלת את מה שהמשתמש
הרגע עשה, ואז דוחפת את הביטול בחזרה.

הטביעות נלקחות מהמצב **אחרי** המיזוג, לא מזה שנדחף. אחרת מה שנמשך
מהאדם השני היה נראה כשינוי מקומי בסבב הבא ונדחף בחזרה אליו — הלוך
ושוב בלי סוף. יש בדיקה שמאמתת דווקא את ההתכנסות הזו.

### `rev` ולא חותמת זמן

הלקוח מושך "כל מה שהשתנה מאז הביקור האחרון". שעון לקוח מוטה — בדיוק
מה ש-`normalizeWeekStart` כבר מתגונן מפניו — היה מסמן נקודת ציון
עתידית ומפספס כל שינוי אמיתי עד שהזמן ישיג אותו. מונה עולה שהשרת
מנפיק חסין לזה, וגם לשתי כתיבות באותה אלפית שנייה.

### טביעות ולא עותק

כדי לדעת מה השתנה מקומית צריך לזכור איך המצב נראה בסנכרון האחרון.
עותק מלא היה מכפיל את נפח האחסון המקומי — באפליקציה שכבר הוציאה את
התמונות ל-IndexedDB בגלל מכסת 5MB, זה הכיוון הלא נכון. נשמרת טביעה
כפולה לכל מפתח: מספיק כדי לזהות שינוי, לא מספיק כדי לשחזר ערך, וזה
כל מה שצריך.

### מה לא מסונכרן

**תמונות המנות.** הן ב-IndexedDB ולא ב-store, מאותו נימוק שבגללו הן
גם לא בקובץ הגיבוי. סנכרון שלהן דורש Supabase Storage וזה עוד לא נבנה
— ולכן מכשיר שני יראה את המנות בלי התמונות שלהן.

## עיצוב

**טיפוגרפיה:** `TelAviv Brutalist` לתצוגה, `Alef` לגוף. שניהם כבר היו
ב-`fonts/` ולא היו בשימוש בשום מקום באתר — אין בקשת רשת חיצונית.
ארבעה גדלים בלבד: meta / body / title, ועוד אחד לשם המנה בכרטיס היום.

**הכלל שמכתיב את כל השאר:** מילוי מלא הוא מטבע נדיר, ושמור לפעולה
*אחת* שצריך לעשות עכשיו. מה שהושלם מקבל קו וגוון רך. גרסה קודמת ציירה
"בישלנו" כמלבן ירוק כהה, והתוצאה הייתה ש*ביצוע* נקרא כמשקל — מוסדי,
לא ביתי. אם החרס מופיע פעמיים במסך אחד, אחד מהם טעות.

**פלטה** — אריח מטבח ישראלי:

| טוקן | ערך | שימוש |
|---|---|---|
| `--bg` | `#f7f7f4` | לבן-זיגוג. קר מקרם בכוונה |
| `--ink` | `#1e2430` | שחור כחלחל |
| `--accent` | `#2e5c8a` | קובלט — "היום", "נבחר", "הושלם" |
| `--action` | `#c25339` | חרס — **המילוי המלא היחיד**, וגבולות |
| `--action-text` | `#b04a32` | חרס **כטקסט** בלבד |
| `--attn-*` | צהוב | **רק** כשל אמיתי, לא סטייה |

הכחול נבחר גם מבנית: הוא קר ובהיר, ולכן אינו נהפך לגוש כהה כשממלאים
בו שטח.

**שני טוקנים לחרס, ולמה.** `--action` נבחר כדי לשאת לבן *עליו*, ובתפקיד
הזה הוא עובר. כשהוא עצמו הפך לטקסט על רקע בהיר הוא נפל — 4.26 על `--bg`
ו-3.94 על `--action-soft`. הפיתוי היה להכהות את `--action` עצמו; המחיר
היה שהכפתור הראשי, המילוי המלא היחיד באפליקציה, נעשה כבד ומוסדי — בדיוק
מה שהמערכת הזו נבנתה כדי למנוע. לכן `--action-text`, שעובר 4.5 על כל
משטח באפליקציה (הנמוך ביותר 4.67). גבולות ומתארים נשארים על `--action`:
הם אינם טקסט וסף 3:1 חל עליהם.

במצב כהה החרס כבר בהיר ונושא את עצמו כטקסט (5.50 ומעלה), ולכן שני
הטוקנים שם זהים.

**המדידה נעשית על כל ה-`body`** ולא רק על המסכים — סריקה קודמת שהגבילה
את עצמה ל-`#screen-*` פספסה לגמרי את התפריט התחתון.

**מצב כהה** מולחן ביד ולא היפוך מכני: המשטחים מוגבהים כלפי מעלה
(`--bg` הכהה ביותר, `--surface` בהיר ממנו), והמבטאים הובהרו.

**מסך הפתיחה** משתמש באותם טוקנים בדיוק, ונבדל מהאפליקציה ב**צפיפות
ולא בחומרים**: בלי topbar, בלי tabbar, ובמקצב אנכי רחב יותר. האפליקציה
נסרקת ביד אחת בסופר; את המסך הזה עושים פעם אחת בישיבה. פלטה או
טיפוגרפיה משלו היו קוראות כמו מוצר אחר.

שלושת ריבועי ההתקדמות שם הם **פס השבוע בשלושה**, ובאותה שפת צורות:
מקווקו = שלב שעוד לא הגענו אליו, מסגרת קובלט = השלב הנוכחי, אריח רך עם
וי = שלב שנסגר. זו אינה חזרה לשם עקביות — פס השבוע הוא האלמנט שהמשתמש
פוגש בשנייה שהמסך נסגר, ואם המקווקו והוי כבר אמרו לו משהו כאן, הוא נוחת
על מסך היום כשהוא יודע לקרוא אותו. הצורות מוגדרות פעם אחת ב-CSS
ומשותפות לשני המקומות.
**שני גוונים לנימוק, בלי צבע שלישי.** הצהוב (`--attn`) פסול כאן לפי
הגדרתו — הוא שמור לכשל אמיתי, ו"בישלתם אתמול" היא הסתייגות ולא שגיאה.
לכן קובלט למה שמושך ו-`--ink-soft` למה שמסתייג. הגרסה הראשונה הבדילה
ביניהם בצבע בלבד, וזה נכשל: שני הטוקנים יושבים כמעט על אותה בהירות
(6.4:1 ו-6.2:1 על לבן) ונבדלים בגוון בלבד. **המשקל** הוא שעושה את
ההפרדה בפועל, בערוץ שאינו תלוי בצבע. נופל מזה דבר שלא תוכנן והוא נכון:
מנה שכל נימוקיה אפורים נקראת מיד כמנה שאף סיבה לא מושכת אליה.
**פס ההרכבה** הוא מה שהופך את הבורר ממסך סימונים לכלי החלטה: בזמן
שמרכיבים, הצלחת מסתכמת מולך — זמן, קלוריות וחלבון למנה. זו התשובה
לשאלה "למה להרכיב ולא פשוט לבחור": אפשר לראות מה כל החלפה עושה לפני
שמחליטים. המספרים נגזרים מאותו מנוע של מסך המאקרו, כולל סימון "חלקי",
כי מספר שנראה כמו ידיעה בלי להיות כזו הוא בדיוק מה שהמנוע נועד למנוע.

בכרטיס היום ובמתכנן השבועי ההרכבה נקראת בשתי שורות — הרכיב הראשי
בגודל מלא, והשאר בשורת ליווי רכה ("עם צ'יפס בתנור, סלט ישראלי").
שרשור כל השמות בגודל התצוגה מילא את הכרטיס בשלוש שורות שם ודחף את
"בישלתי" אל מתחת לקיפול.

**האלמנט החתום** הוא פס השבוע: מצב היום *הוא* הצורה, לא תווית לידה —
מקווקו = לא תוכנן, מסגרת = מתוכנן, אריח רך עם וי = בישלנו, אלכסון =
אכלנו בחוץ, קו מוחק = דילגנו. הרצף אינו תג נפרד אלא הריצה של האריחים
שהושלמו. הוי אינו קישוט: בלעדיו "בישלנו" ו"מתוכנן" נבדלו רק בגוון רקע
חיוור, וזה נכשל בדיוק במבחן שהפס קיים בשבילו.

## מה עוד לא נבנה

**מה שנשאר פתוח:**

- **מסך ההתחברות והסנכרון.** התשתית ב-`js/sync/` שלמה ונבדקת, ואין
  לה עדיין ממשק: אין איפה להזין מייל, אין חיווי מצב סנכרון, ואין מסך
  לצירוף האדם השני בקוד הזמנה. `config.js` כבר מלא, ולכן מה שמחזיק
  את השכבה רדומה הוא היעדר הסשן ולא היעדר התצורה — והמסך הזה הוא
  המתג שידליק אותה. המסך עובר דרך צינור העיצוב (`frontend-design`,
  `/design:ux-copy`, `/design:critique`, `/design:accessibility`)
  כמו כל מסך חדש. עד אז הגיבוי לקובץ הוא התחליף החלקי, והוא ידני.
- **תמונות מנה אינן מסונכרנות.** הן ב-IndexedDB, וסנכרון שלהן דורש
  Supabase Storage. מכשיר שני יראה את המנות בלי התמונות.
- **מסך הפתיחה עדיין לא שואל על `dislikes`.** עכשיו כשהשדה חי, זו
  שאלה לגיטימית שם — אבל היא דורשת לבחור מנות מתוך קטלוג של 25 בתוך
  מסך שכל כולו שלוש שאלות. כרגע הסימון נעשה בעורך המנה, בזמן אמת.

**נסגר:**

- **קטלוג זרע של 25 מנות ו-50 מצרכים** (`data.js`). הזרע היה שלוש
  מנות, ומעבר לכך שהתקנה טרייה נחתה בלי מה לתכנן — הבלוק "לא בישלנו
  מזמן" מוסתר מתחת לשבע מנות, ולכן הוא מעולם לא רץ אצל משתמש חדש.
  שבע בדיקות שלמות חדשות, ושתיים מהן תופסות טעות ולא הקלדה: כשרות
  המנה מול המצרכים שלה, והרשימה הסגורה של מנות שנופלות למסלול הידני.
- **`dislikes` חי** — נקבע בעורך המנה, מסומן בבורר, ומסונן מההצעות.
  הנימוק המלא למעלה תחת "החלטות שקל להפוך בטעות".
- **`macros_override` יש לו ממשק** — סקציה מקופלת בעורך המנה, עם
  תמיכה בערכים חלקיים. גם שם למעלה.

- **אונבורדינג** — שלוש שאלות בהתקנה ראשונה (`ui-onboarding.js`).
  נשאל רק מה שמסך קורא בפועל: שמות, אילו ארוחות מתכננים, ויעד קלוריות
  אופציונלי. "כמה זמן יש לבשל" ו"מה לא אוהבים" נשארו בחוץ במכוון —
  אף מסך אינו קורא אותם, והם היו חוזרים על הפגם של `dislikes`.
- **תמונות מנה** (`images.js`). ב-IndexedDB ולא ב-store; הנימוק המלא
  למעלה תחת "החלטות שקל להפוך בטעות".
- **גיבוי לקובץ ושחזור ממנו** (`backup.js`, `ui-backup.js`). נקודת
  הכניסה השנייה היא מסך הפתיחה, ושם היא החשובה: מכשיר חדש הוא בדיוק
  הרגע שבו מחפשים את הכפתור הזה, וזה גם המסך היחיד שרואים בו.
- **"לא בישלנו מזמן"** — היום זו אות דירוג בתוך `suggestDishes`
  (`cookedLongAgo`, אותם 14 יום), ולא רשימה נפרדת. מוצע רק בבורר
  המנה, כי שם המשבצת כבר ידועה והקשה מתכננת מיד; במסך השבוע היה צריך
  לשאול "לאיזה יום?", כלומר להוסיף שלב במקום לחסוך אחד.
  הפונקציה `forgottenDishes` שמימשה את זה בנפרד **הוסרה** אחרי
  שהבורר אוחד — היא נשארה בלי קורא, וקוד מת עם בדיקות ירוקות מזמין
  לחווט אותו בחזרה במקום להרחיב את המנוע שכן פועל.
- **שיתוף רשימת הקניות** (`share.js`). המקרה: אחד מתכנן והשני קונה.
  נכנס לטקסט רק מה שנשאר לקנות — פריט שכבר בעגלה אינו משימה של מי
  שמקבל את ההודעה — ומספר המושמטים נאמר בסוף כדי שההשמטה לא תיראה
  כרשימה שהתקצרה בלי הסבר. הערת "לבדוק ידנית" נשארת, כי היא הדבר
  היחיד שאומר לקונה שהמספר לידה אינו מדויק.
- **ארבעה כשלי ניגודיות מדודים.** שלושה דרך `--action-text`, והרביעי
  היה באג ולא בעיית פלטה: `.item` מרונדר כ-`<li>` ברשימת הקניות
  וכ-`<button>` במזווה, ולכפתור לא הוצהר `background` — בכהה הוא נפל
  ל-`ButtonFace` של הדפדפן. באותה שורה התגלה ש-`.item-name` מעולם לא
  קיבל כלל CSS, ולכן השם והכמות נדבקו ל"בצל300 גרם".

**נדחה במודע:**

- הפחתה אוטומטית מהמזווה (ראה למעלה)
- סנכרון תמונות (דורש Supabase Storage; ראה "מה עוד לא נבנה")

**הוחלט אחרת:** סנכרון בין מכשירים היה שנה תחת "נדחה במודע", בנימוק
שהוא דורש שרת ומשנה את אופי המוצר. מה שהשתנה הוא שהנימוק התברר
כחצי נכון: הוא אכן דורש שרת, אבל לא חייב לשנות את אופי המוצר. השכבה
נבנתה כתוספת שהאחסון המקומי נשאר הבעלים תחתיה, ולכן האפליקציה
שעובדת בלי קליטה בסופר ממשיכה לעבוד בדיוק כך. היא עדיין רדומה, ומה
שמחזיק אותה כך הוא `signedIn()` — ראה "שני שערים" למעלה.
