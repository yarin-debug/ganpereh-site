# מתכנן הארוחות

אפליקציית ווב פרטית לתכנון ארוחות במשק בית. מובייל-תחילה, עברית RTL,
בלי שרת ובלי חשבון — כל המצב יושב ב-`localStorage` של המכשיר.

בלי build, בלי תלויות, בלי בקשות רשת חיצוניות. ES modules טהורים.

---

## המסכים

| טאב | מה הוא עונה עליו |
|---|---|
| **היום** | "מה אוכלים עכשיו" + סימון שזה קרה. טאב ברירת המחדל. |
| **השבוע** | תכנון: איזו מנה בכל משבצת, ואילו ארוחות בכלל מתכננים. |
| **קניות** | מה לקנות, מקובץ למדפי סופר, עם סימון בעגלה. עובד אופליין. |
| **מזווה** | מה כבר בבית. מקוזז אוטומטית מרשימת הקניות. |
| **מאקרו** | מה נאכל בפועל מול היעדים, לכל פרופיל. מתאר, לא שופט. |

## מפת המודולים

**לוגיקה טהורה** — בלי DOM, בלי גישה ל-store, נבדקת ישירות:

| קובץ | אחריות |
|---|---|
| `normalize.js` | המרות יחידות, סכימת רשימת קניות, חישוב מאקרו |
| `plan.js` | ארוחות, מצב יום, רצף בישול, מפתחות שורות קנייה |
| `pantry.js` | קיזוז המזווה מול דרישות השבוע |
| `catalog.js` | מיזוג מנות/מצרכי זרע עם עריכות המשתמש |
| `profiles.js` | מי במשק הבית, יעדים, וניקוי משבצות בהוצאת אדם |
| `history.js` | מתי בישלנו מה, מנות שנשכחו, והעתקת שבוע קודם |
| `backup.js` | עטיפת קובץ הגיבוי, אימות קובץ נכנס, וספירת מה יש בו |
| `share.js` | רשימת הקניות כטקסט להדבקה |

**מצב ונתונים:**

| קובץ | אחריות |
|---|---|
| `store.js` | התמדה, נרמול קלט פגום, גלגול שבוע, סנכרון בין טאבים |
| `data.js` | נתוני זרע — מנות, מצרכים, מדפים. **בקוד, לא באחסון.** |

**ממשק** — `app.js` (רישום מסכים), `ui-today/week/list/pantry/score.js`
(מסכים), `ui-overlay.js` (מחסנית שכבות ולבני טופס), `ui-sheet.js` (בורר
מנה), `ui-dish-editor.js` / `ui-ingredient-editor.js` / `ui-profiles.js`
(טפסים), `ui-strip.js` (פס השבוע), `ui-onboarding.js` (מסך הפתיחה),
`ui-backup.js` (הורדת גיבוי וטעינה ממנו).

**זרימה חד-כיוונית:** המסכים קוראים מה-store וכותבים דרך `store.update`
בלבד. `app.js` מחזיק את המנוי היחיד שמרנדר מחדש. אף מסך לא מייבא בחזרה
מ-`app.js` — אין מעגל תלויות.

## מודל הנתונים

```js
{
  schema_version: 1,
  plan: {
    week_start: "2026-07-26",          // תמיד יום ראשון
    slots: {
      "2026-07-28.dinner": {            // מפתח: תאריך.ארוחה
        dish_id: "dish.schnitzel_chips",
        servings: 2,
        eaters: ["p1", "p2"],
        status: "planned"               // planned | cooked | ate_out | skipped
      }
    },
    checked: { "ing.onion": true }      // סימוני קנייה, מתאפסים בגלגול שבוע
  },
  profiles: [{ id, name_he, targets: { kcal, protein_g, fat_g, carbs_g }, dislikes: [], archived }],
  pantry:      { "ing.onion": { qty: 300, unit: "g" } },
  dishes:      { "dish.u1": { ... } },  // מנות משתמש + עריכות של מנות זרע
  ingredients: { "ing.u1": { ... } },   // מצרכי משתמש
  prefs:       { meals: ["breakfast", "dinner"] },  // אילו ארוחות מתכננים
  onboarded:   true                     // האם מסך הפתיחה הושלם
}
```

### מדיניות סכמה

`SCHEMA_VERSION` הוא **1** ולא עלה מאז. כל התוספות עד היום היו נקיות —
שדות חדשים בלבד. `coerceState` פורס את ה-raw ושומר שדות שהגרסה הזו לא
מכירה, כך שגרסה ישנה במטמון לא מוחקת נתונים של גרסה חדשה.

להעלות את הגרסה **רק** כששינוי אינו תואם אחורה. הערך מנעילת כתיבה
(`schema_version` עתידי → האפליקציה לא כותבת בכלל) גדול מהערך של מספור
מסודר.

## החלטות שקל להפוך בטעות

הרשימה הזו קיימת כדי שהחלטה נכונה לא תתהפך בסיבוב הבא. כל אחת מהן
מתועדת גם בראש הקובץ הרלוונטי.

### אין המרה מנוחשת — בשום מקום

`toBase` מחזיר כמות **מסומנת** כשאי אפשר להמיר, לא שגיאה ולא אפס שקט.
"גביע יוגורט אחד" בלי `unit_weight_g` מגיע לרשימת הקניות כפריט "לבדוק
ידנית" עם הכמות המקורית. אותו כלל בדיוק חל על קיזוז המזווה.

מספר מומצא ברשימת קניות גרוע ממספר חסר — הראשון נראה כמו ידיעה.

### מנות זרע נשארות בקוד; עריכה כותבת העתק

הפיתוי: להעתיק את כל הזרע ל-`localStorage` בטעינה הראשונה ומשם לערוך.
המחיר: תיקון בנתוני זרע (ערך תזונתי שגוי, שם, זמן הכנה) לעולם לא מגיע
למי שכבר פתח את האפליקציה פעם אחת.

לכן `catalog.js` ממזג: הזרע בקוד, עריכה שומרת העתק תחת אותו מזהה,
ההעתק גובר. מחיקת ההעתק היא "שחזור לגרסה המקורית" וקיימת בממשק.

### ארכיון, לא מחיקה — למנות ולאנשים כאחד

משבצות מצביעות על מנה לפי מזהה ושורדות שבועות אחורה. מחיקה הייתה הופכת
כל היסטוריה שמצביעה עליה ל"מנה לא מוכרת" — כולל מסך המאקרו של שבועות
שכבר נאכלו. מנה בארכיון יורדת מהבורר וממשיכה להיפתר בכל מקום אחר.

**אותו נימוק לפרופילים, ובחדות אף גדולה יותר:** `slot.eaters` מחזיק
מזהי אנשים, וחישוב המאקרו מחלק את המנות במספרם. מחיקת פרופיל הייתה
משאירה מזהה יתום בתוך `eaters`, והמחלק היה ממשיך לספור אדם שכבר לא
קיים — כלומר להציג לכל השאר **פחות ממה שהם באמת אכלו**.

הוצאת אדם ממשק הבית מנקה את `eaters` **מהשבוע הנוכחי והלאה בלבד**.
שבועות שעברו נשארים כמו שהם, כי המאקרו שלהם היה נכון כשהוא נאכל.
משבצת שהוא היה האוכל היחיד בה נמחקת — להשאיר אותה עם `eaters` ריק היה
גרוע יותר, כי `coerceSlots` ממלא רשימה ריקה במשק הבית הנוכחי והמנה
הייתה מוקצית בשקט למישהו אחר.

### המזווה לא מתעדכן לבד אחרי "בישלתי"

הפיתוי מובן — סימון הבישול כבר קיים. אבל האפליקציה יודעת כמה המתכון
*נוקב*, לא כמה נכנס לסיר ולא אם נשאר חצי בצל. מלאי שמחסיר מספרים שלא
קרו מצטבר לשקר, והשקר מתבטא במקום הגרוע ביותר: רשימת קניות שמחסירה
פריט שאין בבית.

מזווה ידני שגוי הוא באחריות מי שהקליד. מזווה שמחסיר לבד שגוי בשקט.

### מצרך בלי ערכי תזונה הוא מצב תקין

הדרישה היחידה ליצירת מצרך היא שם. בלי `nutrition_per_100` המנה מסומנת
"חלקי", ובלי `unit_weight_g` היא נופלת למסלול הידני — שני מסלולים
שנבדקים. לחייב ארבעה ערכים כדי להוסיף "פטרוזיליה" היה גורם לאנשים
להמציא מספרים, וזה בדיוק מה שהמנוע נועד למנוע.

ערכים חלקיים (קלוריות וחלבון בלבד) נשמרים חלקיים ומסמנים את המנה
כחלקית — לא מושלמים באפס.

### הריבוע בפס השבוע מתמלא רק כשהיום סגור

כל עוד יש ארוחה מתוכננת שלא הוכרעה, היום "מתוכנן" — גם אם כבר בישלת
בבוקר. אחרת גובר מה שקרה בפועל: בישלנו ← בחוץ ← דילגנו.

**הרצף שואל שאלה אחרת** — "בישלת בבית לפחות ארוחה אחת?" ולא "סגרת את
היום?". ארוחת בוקר מבושלת בזמן שהערב פתוח לא שוברת רצף באמצע היום.
ולהיום יש ארכה: בשש בערב עוד לא בישלת, וזה לא מאפס רצף של שבועיים.

### `onboarded` — אותו שדה, שתי ברירות מחדל

`defaultState` מחזיר `onboarded: false`, ולכן התקנה טרייה עוברת דרך מסך
הפתיחה. `coerceState`, שרץ **רק על בלוב שכבר קיים במכשיר**, מחזיר `true`
כשהשדה חסר.

זה נראה כמו חוסר עקביות והוא הלב של הפיצ'ר: בלוב שנשמר לפני שמסך הפתיחה
נולד שייך בהגדרה למי שכבר עובד עם האפליקציה. לשלוח אותו להגדרה מחדש היה
מציע לו לבנות משק בית שכבר קיים לו, מעל תוכנית שכבר תוכננה — והמסך
מסיים בכתיבה שדורסת את `profiles`. רק `false` מפורש, כלומר מי שפתח את
המסך ולא סיים אותו, מחזיר לשם.

`needsOnboarding()` מכבה את המסך כשכתיבה ממילא תיכשל (סכמה עתידית, או
JSON פגום שלא הצליח להתגבות). מסך שמבקש להגדיר משק בית ואז לא שומר אותו
הוא הבטחה ריקה. אחסון חסום דווקא כן מקבל אותו — שם הסשן הזה עובד,
וההודעה בראש המסך כבר אומרת שהוא לא יישמר.

### ארוחה שכבר תוכננה מוצגת גם כשהיא מחוץ להעדפה

`prefs.meals` הוא סינון **תצוגה** בלבד. `dayState` והרצף מסננים ארוחות
ריקות ממילא, ולכן ארוחה שלא מתכננים פשוט אינה קיימת בעיניהם — אין צורך
לשנות בהם דבר.

אבל ארוחה שכבר יש בה משבצת מוצגת תמיד, גם אחרי שהורידו אותה מההעדפה.
הסתרה שלה הייתה יוצרת נתונים בלתי נראים: המנה ממשיכה להיספר במצב היום,
ברשימת הקניות ובמאקרו, ולמשתמש אין שום מסך שבו הוא יכול לגעת בה. זה
בדיוק הכלל של מצרך לא מזוהה שמוצג ברשימה במקום להישמט בשקט.

ההעדפה ניתנת לשינוי במסך השבוע. בלי זה היא הייתה דלת חד-כיוונית.

### מוצעות רק מנות שכבר בושלו, ורק כשיש ממה לקצר

הפיתוי ב"לא בישלנו מזמן" הוא לדחוף לרשימה גם מנות שמעולם לא בושלו, כדי
שתמיד יהיה מה להציע. הכותרת פשוט אינה נכונה עליהן — וזו אותה משפחה של
שקר קטן שהמנוע נמנע ממנה בכל מקום אחר. מנה שבישלו פעם היא גם המלצה
חזקה יותר: משק הבית כבר הצביע עליה. כשאין מה להציע מחזירים רשימה ריקה
והממשק לא מציג כלום.

הסף הוא **שבועיים**: מנה שבושלה לפני ארבעה ימים אינה "מזמן", וסף נמוך
מדי הופך את ההצעה לרעש שמפסיקים להסתכל עליו. מנה שכבר בתוכנית השבוע
מסוננת — להציע אותה שוב זו בעצמה עייפות תפריט.

והבלוק כולו מוסתר כשבקטלוג פחות משבע מנות: שם ההצעות *הן* הקטלוג,
והן חוזרות מילה במילה על מה שנמצא שורה מתחתיהן, כולל תווית
ה"בישלתם לפני..." שכבר יושבת בכל שורה. הקיצור קיים כדי לחסוך גלילה,
ורשימה שנכנסת למסך אחד אינה דורשת קיצור.

### הייבוא הוא הפעולה היחידה שמוחקת נתונים בכוונה — ולכן גם היא מגבה

כל שאר המנגנון ב-`store.js` מגן מפני *האפליקציה*. הוא לא מגן מפני
הדפדפן: ניקוי נתוני גלישה, פינוי אחסון בספארי או מכשיר חדש מוחקים הכל,
ואין שרת. הקובץ הוא הדרך היחידה להוציא נתונים מהמכשיר, ולכן הוא קיים.

הכיוון המסוכן הוא הייבוא, והוא מציית לאותו כלל של ה-JSON הפגום:
הבלוב הקיים מוצנע תחת `__before_import` **לפני** הכתיבה, ואם ההצנעה
נכשלה — הייבוא לא קורה בכלל. גם כאן המקום הראשון לא נדרס, כך שמי
שייבא פעמיים בטעות מוצא תחת המפתח הראשון את הנתונים האמיתיים שלו ולא
את תוצאת הטעות הקודמת. כתיבה שנכשלה מחזירה את המצב הקודם לזיכרון,
אחרת המסך היה מציג נתונים מיובאים שאינם שמורים בשום מקום.

`readBackup` מקבל **שתי צורות**: את העטיפה שהאפליקציה כותבת, וגם בלוב
מצב חשוף. מי שהעתיק את הערך היישר מ-`localStorage` כדי להציל נתונים
מדפדפן שנתקע מחזיק ביד בדיוק את הצורה השנייה, ולדחות אותו היה לדחות
אותו ברגע שהוא הכי צריך את זה. גיבוי מסכמה **עתידית** נדחה — אותו
נימוק כמו נעילת הכתיבה: עדיף לסרב מאשר לקצץ שדות בשקט.

### מה שמצטמצם בייבוא נאמר במילים, לא בצבע

הגרסה הראשונה של טבלת ההשוואה צבעה בחרס כל מספר שקטן מהקיים. שתי
בעיות: חרס כטקסט נמדד 4.26 ואינו עובר את הסף, וצבע לבדו ממילא אינו
סימן — קורא מסך היה מקבל טבלה של מספרים שווי משקל. משפט אחד מתחת
לטבלה אומר את זה לכולם, ואומר יותר: לא רק *ש*משהו קטן, אלא *מה*.

באותו נימוק, מכשיר שעוד לא הוגדר מקבל טבלה בעמודה אחת. עמודת "עכשיו"
שם הייתה מציגה "2 אנשים" — פרופילי הזרע הבלתי נראים שאיש לא הזין —
ומבטיחה למשתמש שהוא עומד לאבד משהו שאין לו.

### סימון הקנייה נשמר לפי מצרך, לא לפי כמות

שינוי בתוכנית באמצע הקנייה מעדכן את הכמות בשורה אבל לא מוחק את מה שכבר
בעגלה. גלגול שבוע מאפס את הסימונים; את המזווה הוא לא נוגע.

### חלוקת העבודה בין המסכים

המתכנן השבועי קובע *מה* אוכלים. מסך היום קובע כמה מנות, מי אוכל, ומסמן
שזה קרה. בלי החלוקה כרטיס יום היה נושא שלושה סטים של פקדים והמסך היה
מפסיק להיות סריק.

### נתוני משתמש לא נדרסים לעולם

JSON פגום מגובה לפני שנטען מצב התחלתי (ואם הגיבוי נכשל — לא כותבים
בכלל). `schema_version` עתידי נועל את הכתיבה לכל אורך הסשן. חסימת
`localStorage` נופלת לזיכרון עם אזהרה כנה במקום להפיל את האפליקציה.

## עיצוב

**טיפוגרפיה:** `TelAviv Brutalist` לתצוגה, `Alef` לגוף. שניהם כבר היו
ב-`fonts/` ולא היו בשימוש בשום מקום באתר — אין בקשת רשת חיצונית.
ארבעה גדלים בלבד: meta / body / title, ועוד אחד לשם המנה בכרטיס היום.

**הכלל שמכתיב את כל השאר:** מילוי מלא הוא מטבע נדיר, ושמור לפעולה
*אחת* שצריך לעשות עכשיו. מה שהושלם מקבל קו וגוון רך. גרסה קודמת ציירה
"בישלנו" כמלבן ירוק כהה, והתוצאה הייתה ש*ביצוע* נקרא כמשקל — מוסדי,
לא ביתי. אם החרס מופיע פעמיים במסך אחד, אחד מהם טעות.

**פלטה** — אריח מטבח ישראלי:

| טוקן | ערך | שימוש |
|---|---|---|
| `--bg` | `#f7f7f4` | לבן-זיגוג. קר מקרם בכוונה |
| `--ink` | `#1e2430` | שחור כחלחל |
| `--accent` | `#2e5c8a` | קובלט — "היום", "נבחר", "הושלם" |
| `--action` | `#c25339` | חרס — **המילוי המלא היחיד**, וגבולות |
| `--action-text` | `#b04a32` | חרס **כטקסט** בלבד |
| `--attn-*` | צהוב | **רק** כשל אמיתי, לא סטייה |

הכחול נבחר גם מבנית: הוא קר ובהיר, ולכן אינו נהפך לגוש כהה כשממלאים
בו שטח.

**שני טוקנים לחרס, ולמה.** `--action` נבחר כדי לשאת לבן *עליו*, ובתפקיד
הזה הוא עובר. כשהוא עצמו הפך לטקסט על רקע בהיר הוא נפל — 4.26 על `--bg`
ו-3.94 על `--action-soft`. הפיתוי היה להכהות את `--action` עצמו; המחיר
היה שהכפתור הראשי, המילוי המלא היחיד באפליקציה, נעשה כבד ומוסדי — בדיוק
מה שהמערכת הזו נבנתה כדי למנוע. לכן `--action-text`, שעובר 4.5 על כל
משטח באפליקציה (הנמוך ביותר 4.67). גבולות ומתארים נשארים על `--action`:
הם אינם טקסט וסף 3:1 חל עליהם.

במצב כהה החרס כבר בהיר ונושא את עצמו כטקסט (5.50 ומעלה), ולכן שני
הטוקנים שם זהים.

**המדידה נעשית על כל ה-`body`** ולא רק על המסכים — סריקה קודמת שהגבילה
את עצמה ל-`#screen-*` פספסה לגמרי את התפריט התחתון.

**מצב כהה** מולחן ביד ולא היפוך מכני: המשטחים מוגבהים כלפי מעלה
(`--bg` הכהה ביותר, `--surface` בהיר ממנו), והמבטאים הובהרו.

**מסך הפתיחה** משתמש באותם טוקנים בדיוק, ונבדל מהאפליקציה ב**צפיפות
ולא בחומרים**: בלי topbar, בלי tabbar, ובמקצב אנכי רחב יותר. האפליקציה
נסרקת ביד אחת בסופר; את המסך הזה עושים פעם אחת בישיבה. פלטה או
טיפוגרפיה משלו היו קוראות כמו מוצר אחר.

שלושת ריבועי ההתקדמות שם הם **פס השבוע בשלושה**, ובאותה שפת צורות:
מקווקו = שלב שעוד לא הגענו אליו, מסגרת קובלט = השלב הנוכחי, אריח רך עם
וי = שלב שנסגר. זו אינה חזרה לשם עקביות — פס השבוע הוא האלמנט שהמשתמש
פוגש בשנייה שהמסך נסגר, ואם המקווקו והוי כבר אמרו לו משהו כאן, הוא נוחת
על מסך היום כשהוא יודע לקרוא אותו. הצורות מוגדרות פעם אחת ב-CSS
ומשותפות לשני המקומות.

**האלמנט החתום** הוא פס השבוע: מצב היום *הוא* הצורה, לא תווית לידה —
מקווקו = לא תוכנן, מסגרת = מתוכנן, אריח רך עם וי = בישלנו, אלכסון =
אכלנו בחוץ, קו מוחק = דילגנו. הרצף אינו תג נפרד אלא הריצה של האריחים
שהושלמו. הוי אינו קישוט: בלעדיו "בישלנו" ו"מתוכנן" נבדלו רק בגוון רקע
חיוור, וזה נכשל בדיוק במבחן שהפס קיים בשבילו.

### תהליך העבודה על עיצוב

מוגדר ב-`CLAUDE.md` תחת "עבודת עיצוב": סקיל `frontend-design` לכיוון
לפני כתיבת CSS, ו-`/design:ux-copy`, `/design:critique`,
`/design:accessibility` בשלבים שאחריו.

שלושת הדברים שלמעלה — הפלטה, הטיפוגרפיה, ופס השבוע — הם **החלטות
מוכרעות**. הסקילים מעדנים בתוכן ולא מתחילים מהן מחדש.

## מה עוד לא נבנה

**פערים אמיתיים:**

- **אין תמונות מנה.** השוק הוא photography-first; זה הפער הוויזואלי
  הגדול שנותר.
*(ארבעת כשלי הניגודיות שהיו רשומים כאן נסגרו: שלושה דרך `--action-text`,
והרביעי היה באג ולא בעיית פלטה — `.item` מרונדר כ-`<li>` ברשימת הקניות
וכ-`<button>` במזווה, ולכפתור לא הוצהר `background`. בכהה הוא נפל
ל-`ButtonFace` של הדפדפן, `#6b6b6b`. באותה שורה התגלה ש-`.item-name`
מעולם לא קיבל כלל CSS, ולכן השם והכמות נדבקו ל"בצל300 גרם".)*

**נסגר:**

- **אונבורדינג** — שלוש שאלות בהתקנה ראשונה (`ui-onboarding.js`).
  נשאל רק מה שמסך קורא בפועל: שמות, אילו ארוחות מתכננים, ויעד קלוריות
  אופציונלי. "כמה זמן יש לבשל" ו"מה לא אוהבים" נשארו בחוץ במכוון —
  אף מסך אינו קורא אותם, והם היו חוזרים על הפגם של `dislikes`.
  היעדים נשאלים בקלוריות בלבד: ארבעה מספרים כפול מספר האנשים הם טופס
  ולא שאלה, ובדיוק שם נוטשים הגדרה ראשונה.

**נסגר גם:**

- **גיבוי לקובץ ושחזור ממנו** (`backup.js`, `ui-backup.js`). נקודת
  הכניסה השנייה היא מסך הפתיחה, ושם היא החשובה: מכשיר חדש הוא בדיוק
  הרגע שבו מחפשים את הכפתור הזה, וזה גם המסך היחיד שרואים בו.
- **"לא בישלנו מזמן"** (`forgottenDishes` ב-`history.js`). מוצע רק
  בבורר המנה, כי שם המשבצת כבר ידועה והקשה מתכננת מיד; במסך השבוע היה
  צריך לשאול "לאיזה יום?", כלומר להוסיף שלב במקום לחסוך אחד.
- **שיתוף רשימת הקניות** (`share.js`). המקרה: אחד מתכנן והשני קונה.
  נכנס לטקסט רק מה שנשאר לקנות — פריט שכבר בעגלה אינו משימה של מי
  שמקבל את ההודעה — ומספר המושמטים נאמר בסוף כדי שההשמטה לא תיראה
  כרשימה שהתקצרה בלי הסבר. הערת "לבדוק ידנית" נשארת, כי היא הדבר
  היחיד שאומר לקונה שהמספר לידה אינו מדויק.

**נדחה במודע:**

- סנכרון בין מכשירים (דורש שרת — משנה את כל אופי המוצר)
- הפחתה אוטומטית מהמזווה (ראה למעלה)
- `dislikes` בפרופיל קיים במודל ואף אחד לא קורא אותו
- `macros_override` על מנה נתמך במנוע ונשמר בעריכה, אבל אין ממשק
  שקובע אותו (המקרה האמיתי: יודעים קלוריות של מנה במסעדה ולא את הפירוק)
