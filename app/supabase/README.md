# הקמת הסנכרון

חמישה שלבים, פעם אחת. עד שמסיימים אותם האפליקציה עובדת בדיוק כמו
קודם — מקומית, בלי מסך התחברות. אין שלב ביניים שבור.

השלבים מניחים את הפרויקט הקיים של הדשבורד (`ganpereh-dashboard`),
שבו ההתחברות עם גוגל כבר מוגדרת. פרויקט חדש דורש גם הגדרת Google
OAuth מאפס — ראה "פרויקט נפרד" בסוף.

---

## 1. להריץ את ה-SQL

Supabase → **SQL Editor** → New query → להדביק את `meals.sql` → Run.

**לפני ההרצה**: בתחתית הקובץ יש שתי שורות `insert into meals_allowlist`.
להחליף את `gili@example.com` בכתובת הגוגל האמיתית של גילי. זו הכתובת
שאיתה היא תתחבר, ובלעדיה ההתחברות שלה תיחסם.

הקובץ idempotent — אפשר להריץ אותו שוב אחרי כל שינוי ברשימה.

## 2. להוסיף את כתובת החזרה

Supabase → **Authentication → URL Configuration → Redirect URLs**,
ולהוסיף את שתי הכתובות:

```
https://<הדומיין-של-האתר>/app/
http://127.0.0.1:8899/app/
```

השנייה היא לפיתוח מקומי. בלעדיה, התחברות מהמחשב תיפול על
`redirect_to is not allowed`.

הכתובת חייבת לכלול את הלוכסן הסוגר — היא נגזרת ב-`config.js` מ-
`location.pathname`, וזו הצורה שהדפדפן שולח.

## 3. למלא את הפרטים ב-`config.js`

Supabase → **Settings → API**, ומשם:

| שדה ב-`app/js/config.js` | מאיפה |
|---|---|
| `URL` | Project URL |
| `ANON_KEY` | Project API keys → `anon` `public` |

`anon` הוא מפתח ציבורי בכוונת המעצב — הוא לבדו אינו פותח כלום, וכל
ההגנה יושבת ב-RLS שהורץ בשלב 1. את המפתח `service_role` **אין**
להביא לכאן; האפליקציה אינה זקוקה לו.

## 4. להעלות את VERSION ב-`sw.js`

`config.js` הוא חלק מהשלד במטמון. בלי העלאת `VERSION`, המכשירים
ימשיכו להגיש את הגרסה הישנה — בלי הסנכרון.

## 5. להתחבר בשני המכשירים

בפעם הראשונה שירין מתחבר, התוכנית שכבר במכשיר שלו נדחפת למשק הבית
ונעשית המשותפת. כשגילי מתחברת אחריה, היא מקבלת אותה.

---

## מה קורה שם בפועל

| טבלה | תפקיד |
|---|---|
| `meals_allowlist` | מי רשאי, ולאיזה משק בית. אין לקליינטים גישה אליה כלל |
| `meals_households` | מצב האפליקציה כמסמך אחד, עם `meta` (חותמות) ו-`rev` (גרסה) |
| `meals_members` | מי הצטרף בפועל. נכתב ב-`meals_bootstrap` |

הפונקציה `meals_bootstrap()` היא הדרך היחידה להצטרף למשק בית. היא
`security definer` כי משתמש חדש עדיין אינו חבר, ולכן ה-RLS שמגן על
הטבלה חוסם ממנו גם את ההצטרפות אליה.

## להוסיף אדם

שורה ב-`meals_allowlist` (אפשר ישירות ב-Table Editor), ואותו
`household_key` כמו השאר. הוא יצטרף בהתחברות הראשונה שלו.

`profile_id` מקשר את חשבון הגוגל לפרופיל באפליקציה (`p1`, `p2`).
אפשר להשאיר `null` — הקישור אינו נדרש לשום דבר מלבד לדעת מי מסתכל.

## להוציא אדם

למחוק את השורה שלו מ-`meals_allowlist` **וגם** מ-`meals_members`.
מחיקה מ-`allowlist` בלבד מונעת ממנו להצטרף מחדש, אבל החברות הקיימת
שלו ממשיכה לתת גישה.

```sql
delete from meals_members where email = 'someone@example.com';
delete from meals_allowlist where email = 'someone@example.com';
```

## פרויקט נפרד

אם מעדיפים פרויקט Supabase משלו לאפליקציה, נוסף על השלבים שלמעלה:

1. **Google Cloud Console** → Credentials → OAuth 2.0 Client ID (סוג
   Web application). ה-Authorized redirect URI הוא
   `https://<project>.supabase.co/auth/v1/callback`.
2. Supabase → **Authentication → Providers → Google**, להדביק את
   ה-Client ID וה-Client Secret ולהפעיל.

שאר השלבים זהים.

## פתרון תקלות

| מה רואים | מה קרה |
|---|---|
| "החשבון הזה לא רשום למשק הבית" | המייל אינו ב-`meals_allowlist`. לשים לב לאותיות גדולות — הפונקציה משווה באותיות קטנות |
| `redirect_to is not allowed` | שלב 2 לא בוצע, או שהכתובת נרשמה בלי הלוכסן הסוגר |
| השבב מציג "אין רשת" כל הזמן | `URL` או `ANON_KEY` שגויים. הקונסול יראה 401 |
| שינויים לא עוברים בין המכשירים | `VERSION` ב-`sw.js` לא עלה, ואחד המכשירים עדיין על הגרסה הישנה |
